# Local decision protocol

This reference defines the private version-1 protocol between the Kev operation provider and the local Python decision service. It is not the public CLM or OpenRouter System One endpoint. HTTP is loopback-only; authentication and immutable deployment configuration are operator-owned. Request and response byte, item, token, queue, and time limits are explicit service/provider configuration. All failures reject the request without retry, fallback, or truncation.

## Preparation and ranking

`POST /v1/prepare` accepts `{version: 1, deployment, request}`. `request` is the exact UTF-8 JSON text of one official Kev System One request: `{model, state, questions: {transition: {type: "choice", instructions, criteria}}}`. Candidate ids are criteria keys, with complete candidate descriptions as values. The provider serializes this text once and retains it unchanged. The service accepts only its configured model route and one `transition` choice question. `deployment` is `sha256:` plus the SHA-256 of the exact bytes of the locally verified immutable serving manifest, not an echoed route alias. The provider requires it to equal `deploymentManifest.digest`; that verification reference names the same serving manifest. Calibration remains a separate declaration referring to this deployment, not a field that creates a manifest/calibration hash cycle.

Preparation performs no inference. Its response is `{version: 1, deployment, identity, preparation: {requestDigest, tokenizer, serialization, inputTokens, maxInputTokens, tokenIds}}`. `requestDigest` is `sha256:` followed by the lowercase hexadecimal SHA-256 of the exact UTF-8 `request` text. `tokenIds` is the complete ordered sequence produced by the pinned official Kev encoder for this one question; `inputTokens` equals its length. The service must not use a base chat template, approximate independent string counts, silently truncate, or enable unrecorded preprocessing. Token ids and counts are bounded non-negative safe integers; ids are validated against the tokenizer vocabulary. The provider checks response identities, request association, and configured limits before returning a prepared judgment.

`POST /v1/decision` accepts `{version: 1, deployment, request, preparation}`. This complete envelope is `OperationPreparedJudgment.wire`, so existing judgment-request records retain the exact outgoing model request and preparation evidence before inference. The service checks the pinned deployment identity and recomputes the request digest, tokenization, and counts before invoking the pinned official scorer. It returns `{version: 1, deployment, identity, requestDigest, probabilities, result}`. `probabilities` contains the scorer's original full-precision distribution. `result` is the unchanged official System One result containing the model route, rounded `answers.transition`, and honest usage when available. The provider retains both representations, checks their candidate keys and winner agree, and permits only the known four-decimal rounding difference between corresponding probabilities. It validates the full-precision distribution with the runner's existing normalization tolerance; it never renormalizes rounded values or relaxes generic or CLM probability checks. No tool arguments, permissions, replacement candidates, or generated explanations are accepted as decisions.

Both responses include the manifest-owned `identity` view: `{model, wireModel, encoder, tokenizer, serialization, dtype, serviceCaps}`. The provider compares every field with its frozen configuration before using the response. `serviceCaps` contains `maxInputTokens`, `vocabSize`, `maxCandidates`, `maxRequestBytes`, `maxResponseBytes`, `maxQueueSize`, `requestTimeoutMs`, and `executionTimeoutMs`; all numerical values are safe integers in their named units. `vocabSize` covers added and special tokens, not only the base vocabulary. The initial supported precision is `float32`; other precisions require a separately implemented and identified deployment. Position, segment, and readout indices derive deterministically from the complete request and pinned single-question recipe; the worker re-encodes them rather than accepting caller-supplied tensors.

A preparation token sequence is evidence, not authority: callers cannot override the model input by supplying different token ids. A changed encoder, recipe, deployment, limit, or request invalidates preparation. The service and provider do not synthesize CLM billing units or zero output tokens. Serialized answer-token accounting remains separate from claims about generation.

## Optional tokenizer-only service

`POST /v1/tokenize` accepts `{version: 1, tokenizer, texts}` and returns `{version: 1, tokenizer, counts}`, where each entry is `{index, textDigest, tokens}` and `textDigest` hashes the exact UTF-8 source text with the same `sha256:` convention. Only a tokenizer-only deployment with pinned local artifacts exposes this route. Its tokenizer identity binds the artifact inventory, Python and dependency versions, and special-token recipe through the service's manifest-derived identity helper. It loads no model weights and performs no inference. Encoding uses its explicitly pinned special-token recipe, no padding, and no truncation. There is exactly one count for every input in its original order; missing, duplicate, reordered, or mismatched entries fail the client hook. The CLM adapter still owns construction of its independently encoded state/question and candidate texts and enforces its encoder ceiling.

## Lifecycle

The API process owns bounded admission and one supervised inference worker. A queued request cancelled or expired before dispatch never reaches the worker. In-flight work retains ownership until settlement; timeout, cancellation, or shutdown must drain or terminate and join the worker, not merely stop awaiting its response. A failed worker makes the deployment unavailable until explicitly restored; no interrupted request is retried. Request/response bodies, authorization values, and token sequences are not written to service logs. DSH retains its required session evidence in its existing private persistence.

Serving readiness does not attest workload calibration. The operation runner's deployment-verification and calibration checks remain independent and fail closed. Tests use synthetic local backends only; the shipped configuration does not fabricate qualification or activate the service in default DSH profiles.
