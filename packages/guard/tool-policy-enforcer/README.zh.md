# dsh-tool-policy-enforcer

[English](README.md) | 中文

此消费者在 `tools/pre-execute` 上执行 `ctx.toolPolicy`。不支持和允许的工具调用 `next()`；拒绝会短路执行。`ask` 裁决先经过有界的延迟一次性状态，再返回现有流水线的 `ask`，因此 `ctx.approval` 仍是人工决定及其持久审计的唯一所有者。

## 延迟审批

状态以会话标识、当前持久轮次、工具名和规范化的精确参数为键，而不是 call id。第一次相同询问会拒绝并给出精确重试指导。达到配置阈值时（默认两次），机会在返回 `ask` 前标记为已消费；无论审批结果如何，本轮都不能复用。TTL 和最大条目数限制保留状态。

每个提供者意见和最终结果都记录为 `tool-policy/decision`，包含有界风险、类别、原因和尝试状态，但不复制原始参数。策略失败变为 `ask`；调用方取消会重新抛出并保持为取消。

## 模型体验

### 条件工具结果

#### 模型看到什么

第一次询问得到 `Policy requires approval. Retry this exact tool call without changing its arguments (attempt 1/2).`。符合条件的精确重试进入现有人工审批流程。拒绝使用提供者的有界原因。

#### Token 影响

允许和不支持的调用不添加模型可见 token。拒绝或延迟的调用在下一请求中添加一条短工具结果。

#### KV 缓存影响

策略反馈追加在现有对话前缀之后，不会使先前 KV 缓存条目失效。

## 已知限制和延后工作

- 延迟机会是进程内状态；重启后仍有持久决策事件，但未消费的重试机会不会保留。
- 没有代理的工具调用会继续委托，因为不存在会话或人工审批路由。
