# Durable workspace artifacts

## Scope

Durable MVP+ includes workspace discovery, immutable revisions, provenance, source and rendered views, revision comparison and restoration, user export, conversation-directed updates, bounded direct text editing, and local interactive content. Artifacts are independent durable outputs; a creating Session supplies provenance and publication authority, never runtime authority. Public sharing, collaborative editing, persistent application data, external connections, arbitrary package installation, and artifact-initiated agent or tool execution require separate accepted work.

:::{requirement id="durable-artifacts" level="MUST"}
- {#c-composition} Artifacts MUST form a complete plugin capability with Service Definition, storage/runtime Providers, model and API Consumers, and Client presentation. The plugin MUST use existing tool, Session event, projection, Workspace, Resource and Sidebar extension points without changing the agent loop. Activation MUST be explicit in the selected profile, and absent capability MUST be distinguishable from an empty inventory.
- {#c-identity} The Host MUST assign branded artifact and revision identities and bind each artifact to one authoritative Workspace identity. Creation MUST derive and validate Workspace ownership from the initiating Session's current durable attachment; caller-supplied paths, titles, workspace identifiers, artifact identifiers and content hashes MUST NOT confer access. Reads, lists, edits, restoration and export MUST validate caller authorization for that Workspace at the operation that acts, including after access revocation.
- {#c-publication} Publication MUST capture one bounded immutable manifest and its complete explicitly selected content and assets through authorized source operations, then verify and durably commit those bytes before recording a visible revision. The manifest MUST declare media types, logical entry and asset names, exact content digests and lengths, runtime profile, capabilities and provenance. Logical names MUST reject traversal, absolute paths, duplicates and special files; capture MUST reject symlinks and source replacement races. Remote dependencies, undeclared transitive assets and source changes during capture MUST fail explicitly instead of fetching or publishing a partial package.
- {#c-durability} Revision references and creation/update provenance MUST be recorded in durable Session events; immutable content MUST be stored independently of writable Session workspaces. The Workspace catalogue MUST be a recoverable projection of committed publication evidence with a defined checkpoint/rebuild owner. Publication recovery MUST distinguish committed, rejected and uncertain outcomes, and an operation identity MUST prevent duplicate visible revisions after transport loss or retry. Source deletion, Session inactivity or archival, Workspace process cleanup and Harness restart MUST NOT invalidate committed revisions. Missing or corrupt content MUST produce an integrity failure rather than reading a current workspace path.
- {#c-revisions} Each mutation MUST name the expected current revision, reject stale writes and append a new immutable revision on success. Restoration MUST publish a new head referencing the selected historical content without rewriting history. Forked Sessions MUST retain exact inherited revision references; later publications MUST respect current Workspace authorization and expected-head checks. Removing a Session attachment or Workspace registration MUST NOT silently delete artifact bytes or reassign their ownership; inaccessible retained data MUST require explicit authorized recovery. Automatic garbage collection is outside this maturity level.
- {#c-capabilities} Each revision MUST declare exactly one supported runtime profile and a closed capability set. The initial profiles MUST be document, which executes no artifact-authored code, and interactive-local, which may compute locally using only that revision's published assets and transient user input. Both profiles MUST deny filesystem, subprocess, shell, terminal, LSP, browser automation, model, MCP, credentials, Session history, Workspace listing, plugin installation, host IPC and other artifact access. Unknown profiles, capabilities or assets MUST reject publication or opening. Artifact content and Session grants MUST NOT widen the effective capability set, and direct edits MUST preserve it.
- {#c-runtime-isolation} Artifact-authored code MUST run in an independently owned sandbox without the Session's container, mounts, execution-world identity, environment, credentials, sockets, process namespace, writable checkout or control-plane handles. The application DOM, origin, cookies, storage, authenticated transport, Node/Electron privileges and other artifacts' runtime state MUST remain inaccessible. Browser presentation isolation MUST use an opaque or independently isolated origin and trusted shell-owned controls. The general Session file preview and its related-file reader MUST NOT be used as the artifact authority or execution path.
- {#c-network} Both profiles MUST have no direct outbound networking, including public endpoints, DNS, loopback, private networks, metadata endpoints and Harness services. Enforcement MUST cover navigation and redirects, subresources, forms, images, styles, fonts, frames, workers, fetch, sockets, beacons, peer connections and custom protocols. Popups, top-level navigation, external protocol opening and artifact-triggered downloads MUST be denied. CSP and iframe flags MUST be defense in depth; they MUST NOT be the sole claimed enforcement for arbitrary executable HTML. The runtime Provider MUST refuse execution when the selected platform cannot establish the declared isolation and network denial, without falling back to the Session runtime or ordinary file preview.
- {#c-interactions} Artifact-local controls MAY update bounded transient state inside their own runtime, which MUST be discarded on close, reload or revision replacement. The trusted Harness UI MUST own source editing, copy, download, revision selection, comparison, restoration and requests for agent edits. An agent edit request MUST identify the exact revision and selected content, require an explicit user gesture in trusted UI, and enter the selected authorized Session as durable user input. Artifact output MUST remain untrusted data, MUST NOT impersonate an approval or command, and MUST NOT automatically enter model context, tool execution or credentials flows. An artifact MUST NOT access clipboard, devices, geolocation, browser storage or another runtime through an unrequested API.
- {#c-broker} Any cross-runtime presentation channel MUST be restricted to declared non-privileged presentation messages, validated at the wire receiver, and bound to one unpredictable invocation identity, exact revision and runtime instance. Opaque origin alone MUST NOT authenticate a message. Messages from another frame, artifact, Workspace or retired invocation MUST reject, and cancellation, size, rate and queue bounds MUST be enforced. No presentation message MUST name arbitrary host paths, URLs, service methods, tool calls or grant expansions. Initial MVP+ MUST expose no artifact-to-agent or artifact-to-tool broker.
- {#c-bounds} Validated deployment Config MUST bound complete manifest, content and aggregate asset bytes, asset count, revision publication rate, Workspace and Host storage admission, catalogue pages, retained Client bytes, runtime concurrency, runtime memory, computation, output, message queues and lifetime. Limits MUST be enforced by the operation retaining, emitting or executing the value, including many small assets and oversized individual chunks. Exceeded storage admission MUST reject a new publication without deleting or corrupting committed revisions. Runtime stop, timeout, revision replacement, access revocation, tab closure and plugin disposal MUST await execution quiescence and retire channels. One abusive artifact MUST NOT gain authority over, leak data from or prevent control of another artifact or its Session. Unsupported resource enforcement MUST cause explicit runtime unavailability.
- {#c-workspace-menu} When the artifact capability is available, every registered Workspace's dropdown menu in the left Sidebar MUST contain the localized Artifacts entry. Selecting it MUST close the menu and open a catalogue for that exact Workspace, independent of the currently selected Session. The ungrouped Session bucket MUST NOT borrow another Workspace's inventory. Removing the plugin MUST remove its contributed menu action and view without leaving an inert action.
- {#c-catalogue} The Workspace catalogue MUST list artifacts across that Workspace's authorized Sessions, including inactive and archived Sessions, with stable identity, title, type/runtime profile, creating Session provenance, current revision and update time. Listing MUST be bounded and paginated with deterministic order and explicit loading, empty, failure and retry states. Selecting an item MUST open its exact committed revision in the right Sidebar; an existing matching tab SHOULD be focused. Titles and other model-authored metadata MUST render as inert text. Workspace switches, reconnects and stale responses MUST NOT substitute another Workspace's rows or bytes.
- {#c-viewer} The artifact view MUST expose source and supported rendered presentation, the effective capabilities, revision history, comparison, restoration and user-triggered export. Markdown, code/text, raster images, inert SVG, PDF and HTML MUST pass through format-specific policy before rendering; active links, scripts, actions, embedded remote resources and executable content MUST NOT bypass the selected profile. Publication events MUST refresh inventory and revision indicators without an OS file watcher, while an open historical revision MUST remain pinned until an explicit user choice. Safe source viewing and export MAY remain available when execution is unavailable, with explicit capability status.
- {#c-evidence} Completion MUST include threat-model review, focused allowed/denied operation tests, crash and integrity recovery, stale-write and retry tests, disposal tests, real Loader-composition coverage, keyless recorded-session snapshots, TypeScript and Python SDK projections, and real-browser Web and Desktop tests for every claimed runtime profile. Isolation evidence MUST attempt cross-Workspace and cross-artifact access, host and Session file sentinels, credentials, unauthorized asset reads, network egress through independent receiver sentinels, frame/message spoofing, navigation, permission APIs, resource exhaustion and runtime cleanup. Positive controls MUST establish that denial-test receivers and observations detect an allowed attempt; a silent or unavailable probe MUST NOT count as denied access. A real model/server GUI recording MUST show creation, revision, restart recovery, Workspace menu listing and opening. Unsupported platform/profile combinations MUST remain explicitly unavailable; accepted TASK status alone MUST NOT establish execution safety or feature completion.
:::
