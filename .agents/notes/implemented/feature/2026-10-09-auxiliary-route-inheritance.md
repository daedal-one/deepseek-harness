# Agent Note: Auxiliary Session summarizers inherit the main agent's model route

Status: implemented

## Problem

Three auxiliary LLM features each pinned their own provider route in the composition that shipped them. `session-title-llm` serves both title providers, `session-activity-summary-llm` drives the live status in Chat, and `session-summary-llm` writes the durable conversation summary; the last two carried `provider: openrouter` and `model: deepseek/deepseek-v4.1-flash` in seven config fields apiece in `packages/bundle/web-app/cordis.patch.yml`. Every one of those requests therefore ran on a route the user did not select for the work they were doing, and the shipped Web surface could not summarize anything unless the deployment supplied an OpenRouter credential.

The routes were also duplicated knowledge. `agent-default-model` already owns which provider and model the main Agent uses for a Session, and `session-title-llm` already derived its route from that Agent's logged request when no override was configured. The summarizers were the remaining callers that guessed instead of asking.

## Decision

`provider` and `model` become an optional pair on `session-summary-llm` and `session-activity-summary-llm`, following the shape `session-title-llm` established: the fields are declared optional in the validated `Config`, the Loader schema drops `.required()`, and validation rejects a half-supplied pair or an empty string while preserving the absence of both.

Each package resolves its route in one explicit step in its owning implementation, at request time and before any durable record is written. `SummaryRouteResolver.resolve(session)` and `ActivityRouteResolver.resolve(session)` apply the same order: the configured pair wins; otherwise the Session's own logged main-request route from the latest `request/header` event; otherwise the current main-Agent selection read from the optional `agentModels` service through `ctx.get`, passing the Session header's `agentPreset` so a preset's assigned main route is honored. The resolver is the only place that decides, so the request event, the accepted event, and the provider call all carry one resolved route.

That `request/header` source is the Session's own reconstruction of the route its main agent ran under, which the repository already treats as the authority for auxiliary text: `session-title` starts automatic title work only after that header is logged, and `api-session-controller` restores the current selection from the same fold.

When no source carries a route, the request is skipped, not guessed. The resolver writes nothing, appends no request event, reports one warning for that Session — `no main-Agent route is available (no logged request header and no agent-models selection); configure provider and model to pin one` — and returns no route, which the caller turns into the package's existing failure path: `session-summary-llm` keeps its previous accepted summary and `session-activity-summary-llm` keeps its queued batch without setting the state that disables summaries for the Turn. Later requests from the same Session resolve again but stay silent, because an unresolvable route is durable state rather than a transient failure.

The shipped Web composition's `session-activity-summary` and `session-summary` rows keep their pinned route and state in a comment that omitting `provider` and `model` inherits the Session's main-agent route. The recorded-session corpus asserts that exact pinned request — [`snapshots/web/minimal-preset/session.v3.jsonl`](../../../../snapshots/web/minimal-preset/session.v3.jsonl) records a `session/summary-llm-request` carrying `openrouter` and `deepseek/deepseek-v4.1-flash` — so the rows move to inheritance in the same change that re-records those sessions with the pair absent. Inheritance is therefore a shipped capability that any deployment opts into by leaving the pair out, and the product rows follow once their recordings carry the inherited route.

`session-title-llm` is left unchanged on purpose. It shares the optional-pair shape but not the resolution context: its provider interface receives `SessionTitleProviderRequest.route`, and the `session-title` dispatcher passes that route only after the main request header is logged, so an unresolved route there is a caller defect that already fails loudly. The summarizers are triggered by Session events instead and can run before any main request exists, which is why they need the fallback and the skip.

## Alternatives considered

**One shared `auxRoute` config row for all auxiliary features.** A single row naming the auxiliary provider and model would have given deployments one place to control every auxiliary request and would have removed the per-feature duplication the review identified. It lost because it reintroduces the defect at a coarser grain: the auxiliaries would still run on a route chosen for them rather than for the Session, and a user who switches their main model would keep paying for summaries on the old one. It also has no natural owner — the row belongs to no package, so the plugin that consumes it would have to trust a composition convention instead of a validated field.

**Inheriting through the `agent-models` Settings section instead of the service.** Reading the stored per-target selection directly would have honored a saved model without mounting a service, and it is the same data `agent-default-model` publishes. It lost because that section stores only a model and a reasoning effort; the provider comes from the target's deployment-fixed default, so reconstructing a route from settings would duplicate the merge rule that `agent-default-model.currentSelection` and `mainSelection` already own. The task is exactly to reuse that mechanism, not to restate it.

**Injecting `agent-default-model` as a declared dependency.** Declaring the injection would have made the fallback unconditional and the wiring explicit, and it is how `api-session-controller`, `webhook`, and `tool-subagent` consume the service. It lost on build cost and on requiredness: the project-reference closure for the two Session plugins grows from eight entries to the whole agent, credentials, settings, attachment, and typert graph, and both plugins would refuse to mount in a composition that summarizes on a logged header alone. The plugins instead declare the one member they read, `mainSelection`, as an optional `agentModels` service in a local `Context` augmentation; a changed signature in `agent-default-model` fails their compilation rather than drifting, and the augmentation states why the repetition is deliberate.

**Deriving the route from the package-level `ModelSelectionResolver` interface.** Rewriting the resolvers to consume the same injectable abstraction `api-session-controller` uses would have removed the per-package class and left one resolution seam. It lost because that interface also carries the pending session-local selection and the projection-registered preset lookup, neither of which a summarizer may act on: a summary request must not race a pending model switch, and the projection is owned by another package.

**Retrying the skip on the next Turn or batch.** Retrying would recover a Session whose route appears later. It lost because the sources it reads are durable: a missing `request/header` and an unmounted directory do not become present for the same Session, so a retry only repeats the same warning. The activity summarizer's route is resolved before it consumes a batch, so the queued work survives any future fix anyway.

**Recording a dedicated skip event in the Session log.** A `summary/skipped` event would make the reason replayable next to the request events. It lost because the packages' existing convention for auxiliary failure is a warning plus no accepted event, and a new required-on-read Session event would make older builds refuse logs whose only new content is a missing route.

## Consequences

Inheritance is opt-in at the composition that mounts each plugin, and the shipped Web rows stay pinned for now. A deployment that leaves `provider` and `model` out gets summaries on the Session's own route and no longer needs an OpenRouter credential merely because the conversation summary and the live activity status are mounted; its instance spend, rate limits, and provider availability for those two requests follow the agent route, and a misconfigured route fails the auxiliary request the same way it fails the main agent. The rows that still set the pair keep spending that route exactly as before, so the shipped surface's behavior is unchanged by this decision until those rows move.

Two validated `Config` fields changed from required to optional, a pre-stable public API change: every deployment that deliberately pinned a route away from the agent must keep setting the pair, and a half-supplied pair now fails at load with `provider and model must be supplied together`. Deployments that change these rows must keep the pair or inherit.

The resolvable set is strictly narrower than the old pinned one. A Session with no `request/header` in a composition that mounts neither `agent-default-model` nor an explicit pair is never summarized: it logs one warning and produces no value, where the pinned route would have produced one on a credential the user never chose. Named Agent roles are the same trade: their selections live in the directory and are not reachable from a Session alone, so a summarizer that must run on such a role's route keeps an explicit pair.

Each Session's first unresolvable request writes one warning through the logger captured at plugin construction, so the two packages report the same condition once per Session. The knock-on effect of capturing rather than re-reading the context logger is that a test which spies on `ctx.logger.warn` after construction observes nothing; the package suites spy before the plugin mounts.

No snapshot case pins the new behavior, and none was re-recorded: recording needs a provider key that this change did not have. The keyless replay lane replays fixtures whose auxiliary requests recorded the pinned route, which is why the Web rows keep theirs, and the packages' own keyless suites cover the logged-header resolution, the directory fallback, the configured pair, and the skip until those fixtures are re-recorded.
