# Agent Note: Touch boundary and hover-preview guards

Status: implemented

## Problem

The [responsive shell](../feature/2026-08-22-first-party-responsive-web-shell.md) gives Chat main-document scrolling on phones, so a drag beyond the document boundary can invoke browser refresh or history navigation. Hover previews also received the mouse and focus events that mobile browsers synthesize around a tap: `Tooltip` could remain visible while the tapped control stayed focused, and `HoverCard` could arm its dwell without a hover-capable input.

## Decision

The Web shell applies `overscroll-behavior: none` to both `html` and `body`. The standard CSS boundary policy keeps ordinary document scrolling, browser zoom, and component scroll ownership intact while preventing root overscroll from chaining into refresh, history navigation, or bounce effects. The shell does not install a global touch listener.

`HoverCard` opens only when `(hover: hover)` matches. `Tooltip` applies the same capability check to its pointer-hover trigger and records a touch `pointerdown` so the focus event generated by that tap does not open a bubble. Focus without a preceding touch remains an immediate Tooltip trigger, preserving keyboard and assistive-technology access on touch-first devices with attached keyboards. A runtime without `matchMedia` retains the existing hover-enabled behavior.

Capability, not viewport width, owns the preview decision. A narrow desktop with a mouse retains hover previews, while a touch-first device does not gain them merely because its CSS viewport is wide.

## Alternatives considered

**Cancel root `touchmove` events.** Rejected because a global non-passive listener would also mediate legitimate document scrolling and browser zoom, duplicating behavior the CSS overscroll standard already owns.

**Disable previews below the phone breakpoint.** Rejected because viewport width does not identify the active input: desktop windows can be narrow, and tablets or hybrid devices can be wide.

**Suppress every Tooltip focus event when hover is unavailable.** Rejected because touch-first devices may have a hardware keyboard or assistive technology. Suppressing only touch-induced focus removes the sticky tap artifact without deleting the keyboard label path.

**Hide preview CSS under `(hover: none)`.** Rejected because the components would still arm timers, retain open state, and mount portaled content in the accessibility tree. Trigger-level suppression keeps the preview closed.

## Consequences

Root page-edge gestures no longer invoke browser refresh or history navigation, and the shell intentionally gives up boundary bounce effects. Hover cards and pointer-hover tooltips stay absent on touch-first inputs; tapping a Tooltip anchor also closes any visible bubble before focus settles. Keyboard focus continues to expose Tooltip labels regardless of hover capability.

Focused primitive tests pin hover-capability gating, touch-induced focus suppression, keyboard-focus preservation, and child-handler chaining. The assembled phone scenario pins `overscroll-behavior: none` on both root elements while retaining document scrolling and sticky composer reachability.
