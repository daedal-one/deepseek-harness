# Agent Note: 为缓冲后的 LLM 流提供端到端输出速率

Status: implemented

[English](2026-08-17-buffered-stream-output-rate.md) | 中文

## 问题

Web 的 `tok/s` 数字曾用提供方上报的输出 token 数除以本地首 token 到消息的时长。该时长衡量 chunk 到达过程，并不一定衡量模型生成过程：提供方或中间层可以缓冲已生成的响应，使 Harness 在几毫秒内追加数百个 chunk。因此，一个实际会话把 19,523 个输出 token 与 637 毫秒的 chunk 排空时长配对，尽管其请求占用了 185,701 毫秒，最终产生物理上不可信的五位数速率。原有的[延迟／吞吐决策](../feature/2026-08-04-web-latency-throughput-metrics.md)把该失败模式明确保留为回放方差，没有区分传输排空速度与模型输出速率。

## 决策

每个 Web `tok/s` 数字都是端到端输出速率：用提供方上报的输出 token 数除以从 `step/start` 到 `assistant/message` 的完整请求墙钟时间，并且只聚合同时携带两者的步骤。已结算轮次页脚与 Trajectory 计时检查器都从 assistant 节点的 `stepStartTime` 与 `completedTime` 计算；统计条使用 `sessionStats` 字段 `throughputMs` 与 `throughputTokens`，无单元窗口回退镜像这两个字段。首 token chunk 时间只保留为 TTFT 边界，绝不作为输出速率分母。Trajectory 把单独显示的首 token 到完成区间命名为 `Stream span`，而不是生成时间。

完整请求时长包含 TTFT、提供方工作、传输缓冲与任何步内重试延迟。因此它并非纯粹的提供方解码吞吐，而是持久日志可以观察到的诚实速率。只有正时长与有限、非负的输出 token 数才能形成读数；缺失值会被省略，而不是猜测或钳制。

`sessionStats` 投影使用 `stateVersion: 2`，因为持久状态的字段及其语义都发生变化。不匹配的投影缓存会被丢弃并从持久事件日志重建；会话事件与存储格式均不变。

## 考虑过的替代方案

**钳制不可信的值。** 上限只会隐藏症状，同时保留对缓冲区排空速度的测量；不存在能够区分快速模型与缓冲响应的提供方无关阈值。

**保留首 token 到消息的时长，但忽略极短区间。** 最小时长是另一项任意阈值，还会丢掉真实的短响应；它也会继续错误标记耗时较长的缓冲投递。

**移除 `tok/s`。** 省略是诚实的做法，但会放弃现有请求与 usage 事件能够保守支持的有用对比信号。

**使用提供方侧生成计时。** 通用 LLM 协议与持久会话事件均不携带提供方生成时钟。加入提供方专用的后续请求或可选协议字段，会使同一 UI 标签在不同适配器之间无法比较，并在回放时不可用。

## 后果

缓冲后的响应不再根据毫秒级 chunk 排空突发速度产生速率。该数字因包含延迟与重试而低于纯解码吞吐，并且仍因使用墙钟时间而不具确定性。持久投影、窗口回退、已结算页脚、Trajectory 检查器、connection fixture、包文档与聚焦测试共享同一定义；突发回归用例钉住了最终 1 毫秒内投递的 100 个输出 token 必须按完整 5 秒请求计算，结果为 20 tok/s 而非 100,000 tok/s。
